# Lifecycle identity reads — 20 October 2026

The audit of PR #415 at `b2cc9435ab8460cc43a19139bb2f19bce4a6d2c1` reproduced a privacy defect: accepted/completed retries returned an unrelated member's canonical name in retained trade text. The transaction loaded only participant account rows, while response masking treated that subset as the complete identity directory. The baseline regression run had two failures and nine passes; both failures returned `Maya Chen` where the synthetic member's public account ID was required.

The same defect was then reproduced in the scoped purchase-request history, actionable-trade candidate, Trade Room and notification/activity responses. Eight additional regressions against unchanged source produced seven failures and one pass. The passing case was the memory Trade Room path, which already reads the full identity collection. These four read boundaries now also carry the compact directory, with no additional database round trip; their PostgreSQL data and identities come from one statement.

A finite sweep of scoped loaders and redaction consumers also identified marketplace listings and the seller listing workspace. Their directories now cover nested listing/profile text as well. Presence refreshes preserve the metadata on both successful and failed refreshes. The other direct user-collection redactors read complete user collections; authentication and account-profile scopes do not use cross-member free-text masking. Empty candidate/history results skip the directory scan because no request text is returned.

Lifecycle reads now separate complete masking identities from full account records. A compact directory contains only account ID, full name, display-name alias, role information and disabled state. It is read in the same PostgreSQL statement as the canonical transaction snapshot, attached through a private WeakMap, and explicitly retained through store normalization. It is never part of serialized snapshots, persistence, account authorization or account writes. Ordinary snapshots continue to use their full `users` collection. Owner views use canonical names; historical buyer-name fallbacks apply only to public masking.

The full account read is scoped for `accepted`, `payment_sent`, `funds_received`, `usdt_release_pending`, `usdt_sent` and `completed`. These transitions retain the caller, every related request's buyer/seller and all canonical admin/owner notification recipients, including legacy owner-email aliases. Committed retries retain their existing narrower authority read plus the complete identity directory. Callers without an actor ID and other mutation statuses retain their previous full account read. Incomplete legacy request numbering still includes the entire request collection and its participants.

This reduces unrelated credential, verification, profile and bank-detail payloads loaded and normalized inside the financial lock for the four newly scoped progress states. The complete identity scan remains necessary for privacy. A changing action skips it during the optimistic retry probe and performs it in the locked read. No speedup is claimed until the PostgreSQL concurrency harness passes.

The initial lifecycle patch passed 67 focused tests: 34 SQL scope/privacy cases, two directory isolation/serialization cases, 27 lifecycle cases and four public-identity cases. The privacy regression executes the real SQL transaction and store response projection for all six statuses, including public-owner and disabled-owner masking. The expanded scoped-read suite has 16 cases covering PostgreSQL/memory responses, marketplace presence success/outage, seller workspace, raw legacy-owner participant identities and empty responses. Additional helper and owner-history cases cover compact identities and stale saved names. Verification of the expanded patch remains a release gate.

The unchanged-source PostgreSQL 17 control passed all 33 correctness checks and timed 240 actions: median 252.70 ms, p95 561.06 ms, maximum 649.06 ms in the audit sandbox. This is an environment-specific control, not a result for the patch. The earlier CI run exceeded the unchanged 1,000 ms gate; the final patch requires its own correctness and timing run.

There are no schema changes. Transaction locks, durability, authority checks, settlement/commission rules, write allowlists and the existing 1,000 ms per-action timing gate are unchanged. The timing result measures direct server actions, including database lock waiting; it does not establish a universal browser or external-delivery latency guarantee.

Final reviewed candidate validation: 164 focused tests in nine files passed, including all 16 scoped-read API regressions. TypeScript and focused lint both exited 0. Hosted release gates and the candidate PostgreSQL timing/recovery run remain pending at publication.

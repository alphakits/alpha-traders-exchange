# WhatsApp callback persistence failures

Signed Meta and Twilio delivery callbacks returned HTTP 204 when the runtime
database pool was unavailable. Signed STOP callbacks also returned success
(Meta 204, Twilio 200) when either storage or the phone fingerprint secret was
unavailable. Those responses acknowledged work that had not been persisted.

Actionable delivery callbacks now require the existing durable-storage helper.
A valid STOP command requires both its privacy fingerprint and durable storage.
Failures reach the routes' existing HTTP 500 handling; ordinary inbound text
still produces no application action. Invalid phone/message identifiers remain
ignored, and existing signature, provider-account, sender and deduplication
checks are retained.

## Verification

- Eight tests use the actual routes, signature verifiers, parsers and notification
  functions with synthetic signed callbacks and a controlled storage boundary.
- Before repair, all six dependency-failure cases returned a success status and
  failed their assertions. The two ordinary-message cases already passed.
- After repair, all 59 tests across the new suite and five existing webhook,
  notification, delivery-integration and transaction-recovery suites pass.
- No production callbacks, outbound messages, consent changes or financial
  transactions were generated by these tests.

HTTP failure reports the uncommitted work honestly. Actual provider redelivery
depends on its configured retry policy and remains a separate live acceptance
check. This repair is not evidence of inbox delivery or a completed live STOP
journey.
